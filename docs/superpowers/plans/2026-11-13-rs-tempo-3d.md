# RS Tempo 3D — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Visualizador web 3D do Rio Grande do Sul que mostra a previsão do Open-Meteo como nuvens, chuva e raios estilizados sobre uma maquete, com linha do tempo.

**Architecture:** Três camadas que só conversam por interface: `src/data` (grade, fetch, cache, `WeatherField`; puro, não conhece o renderizador), `src/render` (Three.js; consome só `sample/rain/storm/cellInfo`) e `src/ui` (linha do tempo, tooltip, avisos). Toda lógica com regra (campo, relógio, qualidade, luz, slots, decisão de fonte) fica em módulo puro testado com `node --test`; o que é visual é verificado por roteiros Playwright que leem um gancho `window.__rs`.

**Tech Stack:** HTML + ES modules sem build, Three.js 0.187.0 vendorizado, `node --test` (Node 22), Playwright/Chromium já instalados, mapshaper 0.7.101 só no `build-geo`.

**Spec:** `DESIGN.md` na raiz do projeto (cópia do design v2). O executor lê os dois; onde este plano fixa um valor que o design deixou aberto, vale o plano e a escolha vai para o README, seção "Decisões".

## Global Constraints

- Sem build. Só caminhos relativos. Nenhuma requisição em tempo de execução além de `api.open-meteo.com`.
- Única biblioteca em runtime: Three.js **0.187.0**, em `vendor/three/`, via import map local. `OrbitControls` vem do mesmo pacote.
- Testes: `node --test test/`, sem dependências. Aleatoriedade sempre com PRNG semeado (`mulberry32`).
- Roteiros Playwright são `.cjs` (o `require('playwright')` global não resolve em ESM) e rodam só com `?demo=1` ou `?fixture=1`, ou com a API interceptada por `page.route`.
- Não usar `localStorage` para dados. Cache em IndexedDB.
- Textos em português. Horários via `Intl` com `timeZone: 'America/Sao_Paulo'`, a partir de unix.
- Nunca apresentar dado sintético ou gravado como dado ao vivo.
- Tetos (nível alto): 6.000 puffs, 15.000 traços, 12 draw calls, pixel ratio ≤ 1,5.
- Não publicar nada. Não perguntar, não esperar: onde houver margem, escolher e anotar em uma linha no README.
- Cada task termina com commit no repositório local `/home/user/rs-tempo-3d`.
- fps em Chromium headless não é prova de desempenho; o README diz isso.

## Convenções compartilhadas (todas as tasks)

**Cena:** `y` para cima, norte = `-z`, leste = `+x`. Topo do mapa em `y = 0`, corpo até `y = -1`, chão em `y = -1,05`. 1 unidade = 10 km. Camadas de nuvem em `y` = 4 / 7 / 10.

**Tempo:** `t` = horas fracionárias desde `series.times[0]`. Hora ativa de chuva e trovoada: `h = clamp(ceil(t), 0, nT-1)`; fração no intervalo `f = t - (h-1)`, com `f = 1` quando `t = 0`.

**Tipos (objetos simples, sem classes):**

```js
// Grid — src/data/grid.js
{ lon0, lat0, step, nx, ny, nP,
  lons: Float32Array(nP), lats: Float32Array(nP),
  index: Int32Array(nx*ny),          // célula da malha -> p, ou -1
  nearest(lon, lat) -> p,            // nó mais próximo (arredonda; se -1, busca bruta)
  distCells(lon, lat) -> number }    // distância ao nó mais próximo, em células

// Series — índice [p*nT + h]
{ nP, nT, times: Float64Array(nT),   // unix em segundos (UTC)
  low, mid, high, code: Uint8Array,  // cobertura 0–100; weather_code
  precip, windSpeed, windDir: Float32Array }  // mm, km/h, graus (de onde vem)

// Field — implementado por analyticField (Task 2) e createWeatherField (Task 4)
{ nT, times,
  sample(lon, lat, t, out?) -> { low, mid, high, u, v, speed },  // u leste, v norte, km/h, para onde sopra
  rain(lon, lat, t) -> mmPorHora,
  storm(lon, lat, t) -> boolean,
  cellInfo(lon, lat, t) -> { p, lon, lat, h, low, mid, high, precip, code, windSpeed, windDir } | null }

// Status da fonte — src/data/source.js
{ kind: 'live' | 'cache' | 'stale' | 'demo' | 'demo-fallback' | 'fixture', fetchedAt: unixSegundos }
```

**Parâmetros de URL:** `demo=1`, `fixture=1`, `debug=1` (design 5.5) mais dois só para os roteiros: `t=<horas após "agora">` (inicia pausado nesse instante) e `cam=top|se|sw|ne|nw` (pula o voo de abertura).

**Gancho de teste:** com `debug=1`, `window.__rs = { ready: Promise, clock, field, grid, stats(), rainColumns(), firstFrameMs }`. `stats()` devolve `{ fps, frameMs, puffs, drops, drawCalls, quality }`; `rainColumns()` devolve `[{ lon, lat, active }]`.

## Review Focus

Falhas que o design implica mas não lista nos testes. Cada linha tem teste na task dona do código.

1. **API responde 200 com payload ruim** (`error:true`, menos locais que o pedido, séries de tamanhos diferentes, `time` divergente entre lotes): deve contar como falha de rede e seguir a regra 5.4, nunca montar série torta. → Task 5.
2. **Cache inutilizável** (IndexedDB indisponível em aba privada, registro de outro `gridVersion` ou esquema, série que já terminou): seguir como "sem cache", sem exceção não tratada. → Task 6.
3. **Aba volta depois de horas oculta:** `dt` gigante não pode fazer a linha do tempo pular; se o dado passou de 1 h, recarregar. → Task 7 (clamp de `dt`) e Task 9 (recarga).
4. **Bordas do domínio:** `t = 0`, `t = nT-1`, scrub além do fim, ponto fora da grade, canto de célula sem os 4 vizinhos. Nada de `NaN` nem índice fora do array. → Task 4.
5. **Ponteiro fora do estado / sem WebGL / contexto perdido:** tooltip some em vez de mostrar célula distante; sem WebGL aparece mensagem em texto, não tela preta. → Task 8 e Task 9.

### Task 2: Campo analítico, slots e nuvens (etapa 2, parte A)

**Files:**
- Create: `src/data/analytic.js`, `src/render/slots.js`, `src/render/clouds.js`
- Modify: `src/main.js`
- Test: `test/analytic.test.mjs`, `test/slots.test.mjs`

**Interfaces:**
- Consumes: `toScene`, `toLonLat`, `mulberry32`, `smoothstep`, `createScene`.
- Produces:
  - `analyticField({ startUnix, hours = 168, seed = 7 }) -> Field` (mesma interface `Field`; `cellInfo` devolve `null` aqui). Conteúdo fixado pelo design 5.5: ruído suave com buracos de céu limpo (cobertura 0 em pelo menos 20 % da área em qualquer hora), uma faixa de chuva de ~120 km de largura que cruza o estado de oeste a leste em ~36 h e se repete, um núcleo de trovoada de ~60 km de raio dentro da faixa. Onde chove, `low ≥ 70`.
  - `makeSlots({ minX, maxX, minZ, maxZ, count, seed, accept(x, z) }) -> Float32Array` com 5 valores por slot: `x, z, size01, seed01, u`. Malha hexagonal com jitter de 0,4 do espaçamento; `u` uniforme em **[0; 0,9]**.
  - `createClouds({ slotsByLayer: [Float32Array × 3], puffScale }) -> { mesh, count, update(field, t), sort(camera), frame(realSeconds), setSky(sky), setFlashes(list), visibleCount() }`

**Regras fixadas (design 7.3 tornado exato):**
- Cobertura remapeada `c' = clamp((c - 15) / 85, 0, 1)`; presença `a = smoothstep(u, u + 0,1, c')`. (Faixa acima do limiar, não centrada nele: centrada deixaria puff visível abaixo de 15 %.) Escala e opacidade do puff multiplicam por `a`.
- Na camada baixa, se `rain(pos, t) > 0`, usar `c = max(c, 60)` antes do remapeamento.
- Escurecimento: `dark = clamp(rain / 10, 0, 1)`, cor de `#ffffff` a `#4a4f57`, com `rain` avaliado na posição **deslocada** do puff.
- Deriva: órbita elíptica em torno do slot, eixo maior na direção do vento, amplitude `0,35 · CELL · min(1, speed/30)`, eixo menor 30 % disso, velocidade angular proporcional a `speed`. A fórmula roda no vertex shader; a CPU repete a mesma conta a 10 Hz só para saber onde amostrar `rain`.
- Um único `InstancedMesh` para as três camadas (ordenação correta entre camadas). Alpha pré-multiplicado, `depthWrite: false`. `sort(camera)` reordena de trás para frente e só é chamado quando a câmera gira > 5° ou anda > 2 unidades.
- Slots no nível alto: baixa 2.600, média 2.000, alta 1.400 (total 6.000). Tamanho base do puff: baixa 2,2–3,4, média 2,6–4,0 com altura 0,55, alta 3,5–6,0 com altura 0,3 e opacidade máxima 0,35.
- `update` roda a 10 Hz; `frame` só atualiza uniformes.

  - `seriesToApiJson(grid, series) -> object[]` no formato exato da resposta real (um objeto por ponto com `latitude`, `longitude`, `hourly: { time, cloud_cover_low, ... }`).

**Algoritmo de `rain` (o que os testes não determinam sozinhos):**

```
molhada(p, h) = P[p,h] ≥ 0,1
ef(p) = 0, se não molhada(p, h)
      = lerp(molhada(p,h-1) ? P[p,h-1] : 0,  P[p,h],  smoothstep(0, 1/6, f))
        × (h = nT-1 ou molhada(p,h+1) ? 1 : 1 - smoothstep(5/6, 1, f))
rain(lon, lat, t):
  dono = grid.nearest(lon, lat);  se não molhada(dono, h) → 0
  → bilinear de ef() nos cantos presentes (pesos renormalizados)
```

`sample`: bilinear nos 4 cantos da malha, linear entre `floor(t)` e `floor(t)+1`; vento interpolado em componentes `u, v` (pré-calculadas na criação a partir de `windSpeed`/`windDir`), nunca em ângulo. Canto ausente → renormaliza pesos; nenhum canto → valor do nó mais próximo. `t` é limitado a `[0, nT-1]`. `storm`: `code` do nó dono em `h` entre 95 e 99. `cellInfo`: valores brutos do nó dono em `h` (cobertura em `round(t)`), ou `null` se `grid.distCells > 1`.
